# G7 Link Protocol, version 1

> Status: **v1.** Breaking changes need a new protocol version (§13).
> License: CC BY 4.0. Anyone may implement this protocol.

This document specifies how two G7 Link devices find each other, pair,
connect and exchange messages: identity, pairing, the session handshake,
the lanes every message travels on, datagrams, capabilities and the control
messages. Feature services are specified in documents that build on this
one: [notifications](notifications.md), [clipboard](clipboard.md),
[files](files.md), [media](media.md), [actions](actions.md),
[input](remote.md), [toggles](toggles.md), [calls](calls.md),
[contacts](contacts.md), [messages](sms.md), [photos](photos.md),
[storage](storage.md), [deck](deck.md), [mirroring](mirror.md),
[webcam](webcam.md), [microphone](mic.md), [PC capture](pc-capture.md),
[Elevated over USB](elevated-usb.md), [agents](agents.md),
[voice recorder](recorder.md) and [Bluetooth](bluetooth.md). The capability
IDs are listed in [capabilities.md](capabilities.md).

Key words **MUST**, **SHOULD** and **MAY** are used as in RFC 2119.

---

## 1. Concepts

| Term | Meaning |
|---|---|
| **Device** | One installation of G7 Link (a phone, a PC). |
| **Device key** | An Ed25519 key pair generated on first launch. Never leaves the device. |
| **Device ID** | The Ed25519 public key (32 bytes). Equal to the iroh `EndpointId`. Displayed as lowercase z-base-32. |
| **Pairing** | A one-time ceremony after which each device stores the other's Device ID as trusted. |
| **Session** | One authenticated QUIC connection between two paired devices. |
| **Service** | A feature area (`media`, `call`, `agent`, …). Its name is its messages' prefix, its streams' `svc` and its capabilities' prefix. |
| **Lane** | Where a message travels: the control stream, a service's lane, an RPC stream, a media or bulk stream, or a datagram (§4). Every message type has exactly one. |

## 2. Transport

- All traffic runs over **QUIC via iroh**. TLS 1.3 with raw public keys
  authenticates both ends by Device ID. There is no other encryption layer and
  no unencrypted mode.
- **ALPN** values:

  | ALPN | Purpose | Who may connect |
  |---|---|---|
  | `g7link/1` | Sessions | Paired devices only |
  | `g7link-pair/0` | Pairing ceremony (§12) | Anyone, but only while the receiving device is in pairing mode |
  | `g7link/0` | Protocol v0, retired | Accepted only to turn a paired v0 device away (§6.2) |

- A device **MUST** close a `g7link/1` connection immediately (application
  code 2, `UNPAIRED`, §10) if the peer's Device ID is not in its trust store.
- A device **MUST** reject `g7link-pair/0` connections when it is not in
  pairing mode, and **MUST** leave pairing mode after a successful pairing or a
  timeout (default 5 minutes).
- **USB.** Over a USB cable the same QUIC packets travel inside an
  `adb forward` TCP connection to the phone's loopback port `53319` (or one of
  the three after it, one per Android profile). Before any packet, each side
  writes the magic `G7QU` and a length-prefixed JSON hello
  (`{ v: 1, id, name }`, at most 4096 bytes). A hello with another magic is
  refused and the connection closed. Everything after is a session as here.
- **Bluetooth** carries no session. A paired phone and PC may open a small
  encrypted channel over Bluetooth LE ("G7BLE/1") that carries a few control
  envelopes ([Bluetooth](bluetooth.md) §4).

### 2.1 Address discovery

Devices locate each other by Device ID. Implementations use, in order of
preference (iroh races them):

1. Local-network discovery (mDNS address lookup).
2. Last known direct addresses, cached per paired device.
3. Relay servers, only if the user enabled "away from home".

A PC's Bluetooth beacon tells a paired phone that the PC is near, so the
phone dials at once ([Bluetooth](bluetooth.md) §3); a USB cable gives a path
of its own (§2).

What a device's mDNS record (service `g7link`) carries:

| When | Advertised |
|---|---|
| Always (LAN discovery on) | Device ID (the record's name) and direct addresses |
| Only while someone may be pairing with it: its pairing screen or nearby list is open, or it shows a pairing QR code | Also the device's name, in the `user-data` TXT attribute (truncated to fit) |

The name is there so the other device's nearby list can show who it is. Both
pairing screens are open during nearby pairing, so both sides see names then.
At other times the device advertises no name: paired devices find each other
by Device ID, and nothing reads the name for a paired device. A device that
isn't open for pairing may still show up nameless in another device's nearby
list, and refuses pairing (§2) if picked. When the pairing screen closes or
pairing mode ends, the device drops the name from its mDNS record. Internet
lookups (away from home) never carry the name.

## 3. Framing

Every stream carries a sequence of **frames**:

```
frame = length (unsigned LEB128, 1 to 4 bytes) || payload (`length` bytes)
```

- `length` **MUST NOT** exceed 1 MiB (1,048,576) on control, lane and RPC
  streams. Receivers close the stream with `FRAME_TOO_LARGE` otherwise. The cap
  is per frame: an answer longer than a frame comes in parts (§4.4).
- Bulk and media data (file contents, video, sound) does **not** have to use
  frames. After its header frame, such a stream carries what its service
  defines.
- Every frame on control, lane and RPC streams is a CBOR envelope. All CBOR
  payloads are maps. Unknown keys **MUST** be ignored.

### 3.1 Message envelope

| Key | Type | Required | Meaning |
|---|---|---|---|
| `t` | text | yes | Message type, e.g. `hello`, `device.battery` |
| `id` | uint | no | Request ID, unique per stream direction, for requests on control and lanes |
| `re` | uint | no | The `id` this message answers |
| `b` | map | no | Message body (type-specific) |

A frame with both `id` and `re` is `BAD_MESSAGE`. An answer whose request is no
longer waiting is dropped. A receiver that gets an unknown `t` carrying an
`id` **MUST** answer `error UNSUPPORTED`; an unknown `t` without one is
ignored. An RPC request carries no `id`: its stream is the correlation (§4.3).

## 4. Lanes and streams

Every message type has exactly one lane (§9). A message that arrives on the
wrong lane is answered `error BAD_MESSAGE` if it has an `id`, else dropped.

| Lane | Transport | Stream header | Order | Send priority |
|---|---|---|---|---|
| **Control** | the first bidirectional stream, opened by the dialer | none | global | 8 |
| **Service lane** | one long-lived bidirectional stream per service per opener | `{svc, op: "lane", v: 1}` | per service, per direction | 7 for `input`, `call`, `media`; 6 for the rest |
| **RPC** | one bidirectional stream per request | `{svc, op, v: 1}` | none | 4 |
| **Media** | one long-lived stream per media session | the service's | per stream | sound 3 (`mirror/audio`, `mic/pcm`, `media/sound`), video 2 (`mirror/video`, `webcam/video`) |
| **Bulk** | one stream per transfer | the service's | per stream | 0 |
| **Datagram** | QUIC datagram | one tag byte (§5) | none | — |

Priorities are each sender's: they order what it writes, and a responder gives
its answers the priority of the stream they answer.

Every stream but control starts with a **stream header** frame:

```
t = "stream"
b = { svc: text, op: text, v: uint }
```

`svc` names the service, `op` the operation, `v` its version (1 for every
lane and RPC). If the receiver doesn't support it, it answers
`error UNSUPPORTED` and finishes the stream.

### 4.1 Control

Control carries only session housekeeping: `hello`, `hello.update`,
`ping`/`pong`, `device.*`, `pair.revoke`, `ble.key` and `ble.use`. Its
requests carry an `id` and are answered with `re`.

### 4.2 Service lanes

A device opens a lane for a service the first time it has something to send
for it in order, and keeps it for the session, so a service has up to two
lanes, one each way. On its lane the opener sends that service's events and
its ordered requests (with `id`); the other device writes only answers (`ok`,
`error`, with `re`). A receiver handles a lane's frames strictly in the order
they arrive, finishing each before reading the next, so order holds within a
service and nothing one service does can delay another.

Opening a second lane for a service while one is open is refused with
`error BAD_MESSAGE` and the new stream finished. A lane that fails is opened
again on the next send; requests waiting on it fail.

There is no order **across** services, or between a lane and an RPC: a
device that needs one message to follow another sends both on the same lane.

### 4.3 RPC

The opener sends the header, then one request frame `t = "<svc>.<op>"` with
its body and **no** `id`, then finishes its send side. The responder answers
with zero or more `part` frames, then exactly one `ok` or `error`, then
finishes. The body of `part` and `ok` is the operation's answer; `ok` without
a body is a plain success. `re` is not used.

```
→ t = "stream"         b = { svc: "contacts", op: "list", v: 1 }
→ t = "contacts.list"  b = { … }
← t = "part"           b = { contacts: [ … ] }
← t = "ok"             b = { contacts: [ … ] }
```

### 4.4 Paging

An operation marked *paged* (§9.3) has a list answer. The responder splits it
so each `part`, and the `ok`, encodes to at most 256 KiB; a single item larger
than that goes alone in its frame, still under the frame cap. Every `part`
and the `ok` is a whole body of the same type:

- its list is split across them, in order, and the receiver concatenates it;
- the other fields are repeated in each (the receiver keeps the first's);
- a "more" flag (`more`, `more_before`) is set if any frame sets it;
- what only the first frame carries is named in the service's spec (an agent
  page's `asks` and `questions`).

An empty list is one `ok`. A receiver **MAY** give up on an answer of more than
64 MiB or 4096 parts, cancelling it (§4.5).

### 4.5 Cancel

The opener of an RPC cancels it by resetting its send side and stopping its
receive side with application code `CANCELLED` (10). The responder drops the
work, and anything it would still write. Lanes and control have no cancel.

### 4.6 Busy

A responder with more RPCs in flight than it takes (64 per peer), or more
media and bulk streams (32), answers `error BUSY` on the new stream and
finishes it. It never makes the opener wait in silence. A device keeps at
most 16 of its own RPCs in flight to a peer and holds the rest back in order,
so a well-behaved device is never told `BUSY`.

### 4.7 Media and bulk streams

Each service defines its own: files (`files/send`), clipboard images
(`clip/image`), mirroring (`mirror/video`, `mirror/audio`), media
(`media/file`, `media/art`, `media/sound`), storage (`storage/read`,
`storage/write`), webcam (`webcam/video`), microphone (`mic/pcm`), Continuity
Camera (`camera/result`), agents (`agent/export`, `agent/image`,
`agent/thumb`) and pointer motion (`input/motion`). Some start with a request
frame and its answer inside the stream (`media.file` → `media.file.meta`);
those frames are listed in §9.4.

## 5. Datagrams

A QUIC datagram starts with a one-byte tag:

| Tag | Channel | Bytes after the tag |
|---|---|---|
| `0x01` | Pointer motion, scroll, laser ([input](remote.md) §2.1) | a CBOR input event, at most 256 bytes |
| `0x02` | PC sound ([media](media.md) §6) | `seq: u16 LE · ts_ms: u32 LE · codec: u8 · channels: u8 · rate: u32 LE · payload` |

- `seq` counts up by one per sound datagram in a sound session and wraps.
  `ts_ms` is when its first sample was captured, in ms since the sound
  session began.
- `codec` `0` is 16-bit signed little-endian PCM, channels interleaved. The
  other values are reserved; a receiver drops sound in a codec it doesn't know.
- `channels` is 1 or 2, `rate` 8000 to 96000. The payload is whole frames, 1
  to 960 bytes.
- The receiver drops sound whose `seq` is not after the last it played
  (counting on modulo 2^16, less than 2^15 ahead).
- A datagram with an unknown tag is dropped.

When datagrams can't carry a channel (the path's datagram size is too small,
or sending fails), pointer motion goes on an `input/motion` stream and sound
on a `media/sound` stream, never on control.

## 6. Session handshake

After the QUIC handshake, the dialer opens the control stream and sends
`hello`. The listener answers with its own `hello`. The session is
**established** once both are exchanged and the version check passes.

```
t = "hello"
b = {
  proto:   uint,        // protocol version: 1
  app:     text,        // app version, e.g. "0.1.18"
  device:  DeviceInfo,
  caps:    [text],      // capability IDs this device offers (§7)
  power:   text,        // "basic" | "assist" | "elevated" | "n/a" (desktop); unknown values are treated as "basic"
  localsend: text?,     // this device's LocalSend certificate fingerprint (hex), so the
                        // receiver leaves it out of its LocalSend nearby list
}

DeviceInfo = {
  name:       text,         // user-visible name, e.g. "Pixel 9" (receivers keep 64 chars)
  kind:       text,         // "phone" | "tablet" | "desktop" | "laptop"
  os:         text,         // "android" | "linux" (32 chars)
  os_ver:     text,         // "16" / "Ubuntu 24.04 LTS (6.8.0)" (32 chars)
  model:      text?,        // e.g. "Google Pixel 9" (64 chars)
  accent:     uint?,        // optional ARGB seed color (Material You sync)
  screen:     ScreenShape?, // optional measured front-screen geometry (phones/tablets)
  install_id: text?,        // 32 lowercase hex digits: a salted hash that names the physical
                            // device across reinstalls, so a re-paired device replaces its entry
}

ScreenShape = {
  v:           uint?,          // schema version (1)
  aspect:      float,          // upright display width / height (0.2..=5.0)
  corners:     ScreenCorners?, // per-corner radii as fractions of upright screen width (0.0..=0.5)
  cutouts:     [ScreenRect]?,  // up to 8 front cutout bounding boxes in 0.0..=1.0 upright screen coords
  cutout_path: text?,          // optional normalized SVG path (<= 4096 bytes, M/L/H/V/C/Q/Z in 0.0..=1.0)
}

ScreenCorners = { tl: float, tr: float, br: float, bl: float }
ScreenRect    = { x: float, y: float, w: float, h: float }
```

Either device may send `hello.update` on control at any time (for example when
its power level or capabilities change):

```
t = "hello.update"
b = { caps: [text]?, power: text?, device: DeviceInfo? }
```

### 6.1 Versions

There is no negotiation. `proto` **MUST** be 1. A device that receives any
other value answers `error VERSION_TOO_OLD` and closes the connection with
code 3. Its UI says which device needs an update: the other one if `proto` is
lower, this one if it is higher.

### 6.2 Telling a v0 device to update

A device keeps accepting the ALPN `g7link/0` only to turn v0 devices away. On
such a connection it opens no stream and reads nothing. If the peer is paired,
the device tells its user that the peer needs an update (at most once a
minute per peer) and closes with code 3 (`VERSION_TOO_OLD`); an unpaired peer
is closed with code 2 (`UNPAIRED`).

A device that dials a paired peer which doesn't speak `g7link/1` sees the QUIC
handshake fail on ALPN, and tells its user that the peer needs an update.

## 7. Capabilities

A capability ID is a lowercase dotted string (`[a-z0-9._-]`, at most 64
bytes) naming something a device *can offer* right now, given its power
level, OS version, permissions and add-ons. Its prefix is its service's name.
Receivers ignore malformed and unknown IDs and anything beyond 256 entries.
Examples:

| Capability | Offered by | Meaning |
|---|---|---|
| `core.ping` | both | Answers ping |
| `device.battery` | both | Sends battery events |
| `notify.mirror` | phone | Can forward notifications |
| `notify.sensitive` | phone | Can forward sensitive (OTP) notifications |
| `clip.read.auto` | phone | Can read the clipboard in the background |
| `mirror.input` | phone | Accepts input while mirrored (Assist and up) |

Each app combines both devices' capabilities with its own local state to
compute the **capability matrix** that drives the UI (see
`docs/architecture/capabilities.md`). The registry of capability IDs is
[capabilities.md](capabilities.md). A device stores a paired peer's
capabilities and replaces them at the peer's next `hello`.

## 8. Control messages

### 8.1 Heartbeat

QUIC keep-alives keep NAT bindings open. In addition, either side **MAY** send:

```
t = "ping"   id = n   b = { ts: uint }        // sender's monotonic ms
t = "pong"   re = n   b = { ts: uint }        // echoes ts
```

A device pings every 15 s, and every 5 s while its app is in front, and
measures round-trip time from `ping`/`pong` for the connection-health
indicator.

### 8.2 Device events

```
t = "device.battery"
b = {
  level:     uint (0 to 100),
  charging:  bool,
  plugged:   text? ("ac"|"usb"|"wireless"),
  full_in:   uint? (estimated minutes until full, 1 to 1440, when charging and known),
  cell_bars: uint? (0 to 4, cellular signal strength in bars, when known),
  cell_type: text? (cellular network generation/type, e.g. "5G", "LTE", "4G", "3G", "2G"),
  wifi_bars: uint? (0 to 4, Wi-Fi signal strength in bars, when connected to Wi-Fi and known),
}

t = "device.info"
b = DeviceInfo                      // name, accent or screen shape changed

t = "device.update"                 // to peers that offer update.hint
b = {
  channel: text ("stable"|"nightly"),
  version: text (at most 64 characters: digits, letters, ".", "-", "+"),
}
```

`device.update` says a new G7 Link build is out on `channel`. The device that
checks for updates (usually the PC, which is plugged in) sends it when it sees
a new build, and once to each peer that connects later; a phone that sees one
first sends it too. It's only a hint: a receiver checks the channel's feed
itself before installing anything, ignores a malformed one, and starts a
check at most every few minutes however many arrive.

### 8.3 Find my device

```
t = "device.ring"          id = n   b = { on: bool, token: uint? }
t = "ok"                   re = n
t = "device.ring_stopped"           b = { token: uint }
```

A start may carry a token so the receiving device can report when it stops
ringing, including after a local dismissal or timeout. A stop with a token
applies to the matching alarm from that peer. The initiating device clears
its ringing state after a minute if no stop report arrives.

### 8.4 Bluetooth keys

`ble.key` (PC → phone) hands a paired phone the pair's link secret, and
`ble.use` (phone → PC, answered `ble.use`) asks the PC to hold its Bluetooth
link; both are specified in [Bluetooth](bluetooth.md) §2 and §4.5.
`pair.revoke` is §12.5.

### 8.5 Errors

```
t = "error"   re = n?   b = { code: text, msg: text? }
```

On an RPC stream `error` has no `re` and ends the answer.

| `media/art` | `media.art` → `media.art.meta` |
| `storage/read` | `storage.read` → `storage.read.meta` |
| `storage/write` | `storage.write` → `storage.write.accept`, `storage.write.done` |
| `camera/result` | `camera.capture.meta` |
| `agent/export` | `agent.export` → `agent.export.meta` |
| `agent/image` | `agent.image.meta` → `agent.image` |
| `agent/thumb` | `agent.image.thumb` → `agent.image.thumb.meta` |
| `input/motion` | `input.event` (pointer motion, scroll, laser) |
| `media/sound` | sound datagrams without their tag (§5), not envelopes |

### 9.5 Elsewhere

The pairing ceremony's `pair.request`, `pair.accept`, `pair.commit`,
`pair.nonce`, `pair.reveal`, `pair.confirm` and `pair.done` travel on
`g7link-pair/0` connections (§12), never in a session. `ble.otp` travels only
on the Bluetooth channel ([Bluetooth](bluetooth.md) §4.4).

## 10. Error and close codes

| Code | Number | Meaning |
|---|---|---|
| `UNSUPPORTED` | 1 | Unknown message type, service or operation version |
| `UNPAIRED` | 2 | Peer is not in the trust store |
| `VERSION_TOO_OLD` | 3 | The peer speaks another protocol version (§6.1) |
| `FRAME_TOO_LARGE` | 4 | Frame exceeds the size limit |
| `BAD_MESSAGE` | 5 | Malformed CBOR, missing required fields, or a message on the wrong lane |
| `DENIED` | 6 | The user or a per-device permission denied the operation |
| `BUSY` | 7 | Too much in flight; try again later (§4.6) |
| `INTERNAL` | 8 | Unexpected failure on the receiver |
| `NOT_FOUND` | 9 | The thing the request names no longer exists (e.g. a dismissed notification) |
| `CANCELLED` | 10 | The opener gave up on an RPC (§4.5) |

The code goes in an `error` body; the number is the QUIC application code that
closes a connection or resets a stream for the same reason. Services define
their own stream reset codes besides these (`files` resets a transfer with 10
when cancelled and 11 when paused; `mirror` uses 11, `webcam` 12, `mic` 13 when
stopped).

## 11. Security notes

- Device keys are stored encrypted at rest where the platform allows it: on
  Linux, sealed with a key held by the desktop's Secret Service (a private
  `0600` file when no keyring is available); on Android, wrapped with the
  Android Keystore.
- The pairing secret is single-use, kept only in memory, and expires with
  pairing mode.
- Implementations **MUST NOT** log message bodies of notification, message,
  clipboard or file-name content.
- Frame and message decoders are fuzzed in CI.

## 12. Pairing (`g7link-pair/0`)

Pairing has its own version, 0, and is unchanged in protocol v1. It
establishes mutual trust between two Device IDs. Two flows are defined. Both
run over a `g7link-pair/0` QUIC connection, so the TLS layer already
authenticates the raw public keys; the ceremony proves that the **human**
intended *this* peer.

### 12.1 QR flow (primary)

1. The PC enters pairing mode, generates a random 128-bit **pairing secret**
   `S`, and shows a QR code containing a pairing URI:

   ```
   g7link://pair?v=0&id=<pc device id, z-base-32>&s=<S, base64url>&n=<pc name, percent-encoded>[&a=<ip:port>,...]
   ```

2. The phone scans it with its own camera screen and dials the PC's Device
   ID with ALPN `g7link-pair/0`.
3. The phone sends:

   ```
   t = "pair.request"   id = 1
   b = { device: DeviceInfo,
         proof: bytes }   // HMAC-SHA256(S, "g7link-pair-v0" || phone_id || pc_id)
   ```

4. The PC verifies `proof` against the phone's TLS-authenticated Device ID. On
   success it answers:

   ```
   t = "pair.accept"    re = 1   b = { device: DeviceInfo }
   ```

   On failure it answers `error DENIED` and leaves pairing mode after 5 failed
   attempts.
5. The ceremony finishes as described in §12.4, after which the phone opens a
   session (`g7link/1`).

Because the phone learned the PC's Device ID from the QR code and the PC
verifies knowledge of `S`, both directions are authenticated with no codes to
compare.

#### Links from another app

The proof above only holds when the phone read the link off the PC's screen
itself. A `g7link://pair` link that another app hands the phone (a browser, a
chat, the system camera) may have been made by anyone, with their own Device
ID and secret. A static code derived from the link can't tell such a link from
the real one: a 6-digit value of a public ID can be matched offline by trying
about a million keys.

So a phone that receives a pairing link from another app **MUST NOT** run the
QR flow with it. It dials the Device ID in the link (at the addresses in `a`)
and runs the nearby flow (§12.2) instead, as initiator: both screens show a
fresh code from the committed nonces, and both users confirm. The secret `s`
isn't sent. A substituted link reaches the attacker's device, and the user's
own PC shows no code. A host accepts this as any nearby ceremony, while it is
in pairing mode (its QR code shown). If the host refuses it (closed with
`DENIED`, or `error UNSUPPORTED`), pairing fails; the phone never falls back
to sending the proof.

### 12.2 Nearby flow (numeric comparison)

Used when the user picks a discovered device instead of scanning, and for a
pairing link that came from another app (§12.1). The initiator is **A**, the
responder **B**.

1. A → B: `pair.commit { device, c }` where `c = SHA-256(nA)` and `nA` is a
   random 16-byte nonce.
2. B → A: `pair.nonce { device, nB }` with a random 16-byte nonce `nB`.
3. A → B: `pair.reveal { nA }`. B checks `SHA-256(nA) == c`.
4. Both compute the **short authentication string**:

   ```
   sas = uint32(HMAC-SHA256(nA || nB, "g7link-sas-v0" || idA || idB)[0..4]) mod 1,000,000
   ```

   shown as a 6-digit code on both screens.
5. The user confirms the codes match on **both** devices. A sends
   `pair.confirm` as soon as its user confirms. B answers `pair.confirm` only
   after both its own user and A confirmed, so B always sends the last
   message. A decline on either side is sent as `error DENIED` and ends the
   ceremony immediately.
6. The ceremony finishes as described in §12.4.

The commitment in step 1 prevents an attacker from choosing a nonce to force a
matching code; a man-in-the-middle would have different Device IDs on each
side and therefore different codes.

### 12.3 USB flow

Over a USB tunnel (§2) the PC starts the nearby flow (§12.2) by itself when it
finds an unpaired phone. A phone accepts a pairing over its USB tunnel only
while its own pairing screen ("Pair with PC") is open or it is in pairing
mode; otherwise it refuses it like any pairing outside pairing mode (closed
with `DENIED`, "not pairing"), because any app on the phone can reach the
tunnel's loopback port. The PC doesn't report a refused attempt it started by
itself. When the phone's pairing screen opens, the phone starts the nearby
flow with each unpaired PC it's plugged into. A PC still takes a pairing over
a USB tunnel it dialed itself (to a phone it found over ADB) without being in
pairing mode; both users still compare and confirm the code.

### 12.4 Finishing a ceremony

A QUIC connection close discards data the peer hasn't read yet, so the end of
a ceremony is acknowledged explicitly:

1. The host (B) sends the last protocol message (`pair.accept` or
   `pair.confirm`).
2. The initiator (A) answers `t = "pair.done"` and finishes its stream.
3. The host, after reading `pair.done`, stores the initiator as trusted and
   closes the connection with application code **0**.
4. The initiator stores the host as trusted only when it observes the close
   with code 0.

Any failure closes with application code **1** and neither side stores
anything. A host that fails waits briefly (up to 2 s) for the initiator to
close first, so its `error` message is read before the connection goes away.

### 12.5 Unpairing

Either device may send `pair.revoke` on control, then deletes the trust
entry. A device receiving it deletes its entry too. Unpairing locally without
notifying the peer is always allowed; the peer will then be refused with
`UNPAIRED` on its next connection attempt.

## 13. Compatibility rules

1. Adding a message type, a field, a capability, an operation or a service is
   **not** a breaking change. A receiver ignores unknown fields, and answers
   an unknown operation `UNSUPPORTED`.
2. Removing or changing the meaning of a field, message or operation **is**
   breaking: it needs a new operation version (`v` in its header), a new
   message type, or a new protocol version.
3. A capability means "can do this right now". A changed message gets a new
   type or operation version, not a numbered capability.
4. A new protocol version gets a new session ALPN. A device keeps accepting
   the previous one only to tell its user which device needs an update (§6.2).

## 14. Continuity Camera (`camera.capture.*`)

A paired PC that announces `camera.continuity` can ask a paired phone that
announces `camera.capture` to open its camera UI and capture either a still
photo (`"photo"`) or a perspective-cropped, contrast-enhanced document scan
(`"scan"`). Continuity Camera is gated by the per-device `"photos"` toggle on
both ends.

### 14.1 Messages

- RPC `camera/capture.request` (PC → phone): `t = "camera.capture.request"`,
  `b = { request_id: text, mode: "photo" | "scan" }` (`request_id` is 1..=64
  non-control bytes). The phone answers `ok` with `b = { request_id: text }`
  once its capture UI is open, or `error`.
- `camera.capture.cancel` on the `camera` lane (either way):
  `{ request_id: text, reason?: text }`, to cancel a capture in flight (or
  sent by the phone if `"photos"` sharing is off or the camera UI can't be
  opened).

### 14.2 Result stream (`svc = "camera"`, `op = "result"`, `v = 1`)

When the user accepts the captured photo or scanned document on the phone:

1. The phone opens a bidirectional QUIC stream and sends the stream header:
   `t = "stream"`, `b = { svc: "camera", op: "result", v: 1 }`.
2. Next, the phone sends a metadata frame:
   `t = "camera.capture.meta"`,
   `b = { request_id: text, mode: "photo" | "scan", file_name: text, mime: "image/jpeg" | "image/png", size: uint, width: uint, height: uint }`
   (`1 <= size <= 33_554_432` bytes, `file_name` up to 255 bytes).
3. Immediately after the metadata frame, the phone writes `size` raw image
   bytes and finishes its send side.
4. The PC saves a copy into its downloads directory, answers `t = "ok"` (or
   `t = "error"` if denied or malformed), finishes its send side, records a
   `Photo` entry in the local timeline, and surfaces the image to the UI for
   one-click clipboard copy, Save As, or drag-and-drop.

A capture the PC asks for on behalf of a coding agent (the Agents page's or
the launcher's "Take a photo with <phone>") is the same exchange; only the PC
handles it differently: it saves no copy, records no timeline entry, and hands
the picture to the agent host, which re-encodes it without its metadata. It
asks only a phone that's connected, and never queues the request.

## 15. LocalSend v2.1 Interoperability (Optional LAN Interop)

In addition to G7 Link's native QUIC/iroh protocol, any G7 Link node can
optionally enable **LocalSend v2.1** interoperability (off by default, stored in
the local settings table as `localsend.enabled`) to send files to and receive
files from unpaired LocalSend devices on the local network. It is not part of
a session and is unchanged in protocol v1.

### 15.1 Discovery & Coexistence

- **Multicast group:** UDP `224.0.0.167:53317` (`SO_REUSEADDR` enabled so
  multiple listeners can share the multicast group).
- **HTTP/HTTPS server port:** TCP `53317` by default (configurable via
  `NodeConfig::localsend_port` or `G7LINK_LOCALSEND_PORT`). The TCP listener
  peeks at the first byte of each incoming connection (`0x16` = TLS ClientHello)
  to serve both HTTPS and plain HTTP on the same socket.
- **Coexistence:** If TCP port `53317` is already bound by a standalone
  LocalSend app on the same machine, G7 Link logs a warning, sets
  `localsend_receiving() = false` (leaving incoming transfers to the standalone
  LocalSend app), and still joins UDP multicast discovery and supports outgoing
  transfers to discovered LocalSend peers.
- **Identity & TLS:** G7 Link generates a deterministic self-signed X.509 v3
  certificate (Ed25519) from the node's device key and advertises its uppercase
  hex SHA-256 DER digest as the LocalSend `fingerprint`. If a peer's fingerprint
  matches a paired G7 Link `DeviceId`, it is de-duplicated in favor of the
  native G7 Link session; otherwise a deterministic synthetic `DeviceId` is
  derived from `BLAKE3("g7link-localsend-peer-v1:" || fingerprint_or_addr)`.

### 15.2 REST Endpoints (`/api/localsend/v2/...`)

- `GET /api/localsend/v2/info` (and `GET /api/localsend/v1/info`): returns
  `{ alias, version: "2.1", deviceModel, deviceType, fingerprint, download: false }`.
- `POST /api/localsend/v2/register` (and `POST /api/localsend/v1/register`):
  records the announcing peer in the in-memory `LocalSendPeer` table and replies
  with this node's info JSON.
- `POST /api/localsend/v2/prepare-upload`: validates the incoming file manifest
  (up to 1,000 files, valid relative paths with no `..` traversal), creates a
  transfer in `TransferState::Requested`, emits `NodeEvent::TransferUpdated`,
  and waits up to 60 seconds for explicit user consent (`accept_transfer` or
  `cancel_transfer`) before returning `{ sessionId, files: { fileId: token } }`
  or HTTP `403` when declined.
- `POST /api/localsend/v2/upload?sessionId=...&fileId=...&token=...`: streams
  the raw request body to a `.part` file in the downloads folder, atomically
  renames it to the final destination path on completion, updates
  `NodeEvent::TransferUpdated`, and records the completed transfer in the
  timeline and received-files store.
- `POST /api/localsend/v2/cancel?sessionId=...`: cancels an in-flight upload
  session and transitions the transfer to `TransferState::Cancelled`.
